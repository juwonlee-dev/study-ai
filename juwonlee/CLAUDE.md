# CLAUDE.md

LLM이 코딩할 때 흔히 저지르는 실수를 줄이기 위한 행동 지침이다. 필요하면 프로젝트별 지침과 함께 적용한다.

**트레이드오프:** 이 지침은 속도보다 신중함을 우선한다. 사소한 작업에는 상황에 맞게 판단한다.

## 1. 코딩 전에 생각하기

**추측하지 않는다. 혼란을 숨기지 않는다. 트레이드오프를 드러낸다.**

구현하기 전에:
- 가정을 명시적으로 밝힌다. 확실하지 않으면 묻는다.
- 해석이 여러 가지라면 조용히 하나를 고르지 말고 선택지를 제시한다.
- 더 단순한 방법이 있으면 말한다. 필요하면 반대 의견을 낸다.
- 불분명한 점이 있으면 멈춘다. 무엇이 헷갈리는지 짚고 묻는다.

## 2. 단순함 우선

**문제를 해결하는 최소한의 코드만 작성한다. 추측성 코드는 쓰지 않는다.**

- 요청받지 않은 기능은 넣지 않는다.
- 한 번만 쓰이는 코드를 위해 추상화하지 않는다.
- 요청받지 않은 "유연성"이나 "설정 가능성"을 만들지 않는다.
- 일어날 수 없는 상황에 대한 오류 처리는 하지 않는다.
- 200줄로 쓴 코드가 50줄로 가능하다면 다시 쓴다.

스스로 물어본다: "시니어 엔지니어가 보면 과하게 복잡하다고 할까?" 그렇다면 단순하게 바꾼다.

## 3. 필요한 부분만 고치기

**꼭 필요한 곳만 건드린다. 내가 만든 흔적만 정리한다.**

기존 코드를 수정할 때:
- 주변 코드, 주석, 서식을 "개선"하지 않는다.
- 고장 나지 않은 것을 리팩터링하지 않는다.
- 내 방식과 다르더라도 기존 스타일을 따른다.
- 관련 없는 죽은 코드를 발견하면 삭제하지 말고 알린다.

내 변경 때문에 쓰이지 않게 된 것이 생기면:
- 내 변경으로 쓰이지 않게 된 import, 변수, 함수는 제거한다.
- 요청이 없으면 원래 있던 죽은 코드는 제거하지 않는다.

판단 기준: 바뀐 모든 줄이 사용자의 요청과 직접 연결되어야 한다.

## 4. 목표 중심으로 실행하기

**성공 기준을 정한다. 검증될 때까지 반복한다.**

작업을 검증 가능한 목표로 바꾼다:
- "유효성 검사 추가" → "잘못된 입력에 대한 테스트를 작성하고 통과시킨다"
- "버그 수정" → "버그를 재현하는 테스트를 작성하고 통과시킨다"
- "X 리팩터링" → "리팩터링 전후로 테스트가 통과하는지 확인한다"

여러 단계로 이루어진 작업은 간단한 계획을 먼저 밝힌다:
```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

성공 기준이 명확하면 스스로 반복하며 진행할 수 있다. 기준이 모호하면("되게 만들어 줘") 계속 확인을 받아야 한다.
