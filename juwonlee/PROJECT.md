# juwonlee 과제 수행 지침

`juwonlee/` 하위의 모든 과제 작업에 적용한다. 코딩 태도는 [CLAUDE.md](CLAUDE.md)를 함께 따른다.
우선순위: 사용자 요청 > 해당 주차 GitHub Issue > 이 문서. 충돌하면 작업 전에 근거와 선택지를 제시하고 확인받는다.

## 1. 작업 범위

- 파일 생성·수정·삭제·이동은 `juwonlee/` 안에서만 한다. 다른 참여자 폴더와 저장소 공용 파일은 읽기 전용 참고 대상이다.
- `juwonlee/` 밖의 변경이 필요하면 이유와 변경안을 먼저 알리고 승인받는다.
- 임시 파일은 저장소 밖(세션 scratchpad 등)에 만든다. 결과물이 아닌 파일을 `juwonlee/`에 남기지 않는다.
- 기존 변경 사항과 다른 주차 결과물은 과제와 관련 없으면 건드리지 않는다.

## 2. 저장소 공통 규칙 (모든 주차 Issue 공통)

| 항목 | 규칙 |
| --- | --- |
| 작업 경로 | `juwonlee/weekN/` — Issue에 지정된 파일명·경로는 정확히 따른다 |
| 브랜치 | `weekN/juwonlee` → `main` 대상 PR |
| 제출 | 마감 기한까지 PR 제출(미완성이어도 제출), 미완성분은 마감 후 7일 이내 완료 |
| 리뷰어 | `@juwonlee-dev`, `@juhwanHeo` 필수 + 1인 이상 추가. 본인 PR은 본인이 리뷰어가 될 수 없으므로 `@juwonlee-dev` 대신 다른 인원을 추가 지정한다 |
| 병합 | 마지막으로 검토한 리뷰어가 병합하고 브랜치를 삭제한다. 본인 PR을 직접 병합하지 않는다 |
| AI 활용 | 모든 과제는 AI로 수행한다(직접 타이핑 최소화) |
| 대화 기록 | 사용자 프롬프트와 AI 응답을 생략 없이 `prompt.md`로 제출. 여러 AI를 쓰면 `claude-prompt.md`, `codex-prompt.md`처럼 구분 |

## 3. 새 주차 시작 절차

1. `git status`, 현재 브랜치, 기존 변경 사항을 확인한다.
2. `gh issue list --state all`, `gh issue view <번호>`로 해당 주차 Issue를 찾는다. 번호가 불확실하면 제목(`N주차`)으로 후보를 보여 주고 확인받는다.
3. Issue를 다음으로 분류한다: 목표 / 필수 요구사항·완료 조건 / 경로·파일명·도구 제약 / 제출물 / 마감·PR 본문 필수 항목 / 구현과 무관한 운영 안내(스터디 일정, 발표 등).
4. 과제가 여러 Task로 나뉘거나 운영 안내와 섞여 있으면 `juwonlee/weekN/ASSIGNMENT.md`에 과제 수행에 필요한 항목만 정리한다. Issue 번호·URL과 마감을 적고, 원문을 확대 해석하지 않는다.
5. 브랜치가 `weekN/juwonlee`가 아니면 생성 또는 전환을 제안하고 승인 후 수행한다.
6. 구현 범위, 순서, 검증 방법을 계획으로 제시한 뒤 진행한다.

## 4. 수행 원칙

- 기본 언어는 한국어다. 응답, 문서, 주석, 커밋 메시지 설명, PR 본문을 한국어로 쓴다. 코드 식별자, 명령어, 고유명사, Conventional Commits 접두어(`feat(week2):`)처럼 원문 표기가 필요한 부분과 Issue가 다른 언어를 지정한 경우는 예외다.
- 모호하거나 충돌하는 요구사항은 임의로 정하지 않고 묻는다.
- 원본 자료를 바탕으로 한 결과물(예: README → 이미지 → HTML)은 원본에 없는 내용을 추가하거나 바꾸지 않는다.
- 대화 기록 파일은 진행 중에 누적한다. append-only로 지정됐다면 기존 내용을 수정하거나 재정렬하지 않는다.
- 완료 전 과제에 맞는 검증(실행, 브라우저 렌더링, 원본 대조, 정적 검사)을 수행한다. 검증할 수 없는 부분은 수동 확인 항목으로 보고한다.

## 5. Git·GitHub 안전 규칙

- 조회성 명령(`status`, `diff`, `log`, `show`, `gh ... view/list`)은 자유롭게 실행한다.
- 브랜치 생성·전환, 커밋, 푸시, PR 생성·수정, 리뷰 등록처럼 상태를 바꾸는 작업은 명시적 요청이나 승인 후에만 한다. 승인 범위는 해당 작업에 한정된다(브랜치 승인 ≠ 커밋 승인).
- 커밋은 `juwonlee/` 안의 이번 과제 변경만 포함하고, Conventional Commits 형식(`feat(week2): ...`)을 쓴다.
- force push, `reset --hard`, 이력 재작성, 브랜치 삭제는 하지 않는다.
- PR 등록 전에 대화 기록을 최신화해 커밋·푸시하고, PR 본문 초안을 확인받는다.

## 6. PR 본문 기본 구성

작업 내용 / 사용 AI 에이전트·모델(예: Claude Code / Opus 5.5)과 사용 위치·이유 / 검증 방법과 결과 / 결과물 미리보기(이미지 등) / 리뷰어 / `Closes #<Issue>`. Issue가 요구하는 필수 항목을 빠짐없이 넣는다.

- 미리보기·결과물 스크린샷을 PR 본문에 첨부할 때는 저장소에 커밋해 링크하지 않는다. 브랜치가 병합·삭제되면 이미지가 보이지 않을 수 있기 때문이다.
- 대신 `gh attach`(gh 확장 `sudosubin/gh-attach`, 없으면 `gh extension install sudosubin/gh-attach`로 설치)로 `gh attach <파일> -R juwonlee-dev/study-ai`를 실행해 업로드하고, 출력된 `https://github.com/user-attachments/assets/...` URL을 `<img>` 태그로 본문에 넣는다.
- 첨부 후에는 렌더링된 PR 본문에서 이미지가 표시되는지 확인한다.

## 7. 완료 보고

변경 파일, 충족한 요구사항, 검증 결과, 남은 문제를 간결하게 보고한다. `git status`로 `juwonlee/` 밖에 의도하지 않은 변경이 없는지 확인한다. 다음 Git 단계는 제안만 하고 지시를 기다린다.
