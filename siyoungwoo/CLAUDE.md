# CLAUDE.md

이 폴더(`siyoungwoo/`)에서 Claude Code가 작업할 때 따르는 지침이다.

## 1. 저장소 성격

- `juwonlee-dev/study-ai`는 AI 활용 스터디 저장소다. 루트 아래 참여자별 폴더가 있고, `siyoungwoo/`가 우시영의 과제 공간이다.
- 빌드·린트·테스트 도구나 패키지 매니저는 없다. 결과물은 Markdown, 이미지, 정적 HTML/CSS다.
- 과제는 `weekN/` 단위로 쌓인다. 앞 주차 결과물이 다음 주차의 원본이 될 수 있다.
  - `week0/README.md` 자기소개 원본 → `week1/profile.png` → `week2/profile.html`
  - `week3/REPORT.md` 오픈소스(KurbyPdf) 보안 취약점 보고서
- 파생 결과물은 원본에 없는 내용을 더하거나 문구를 바꾸지 않는다.

## 2. 과제 진행 규칙

- 요구사항의 유일한 근거는 GitHub Issue다. 작업 전에 `gh issue view <번호> --json title,body,comments`로 본문을 읽는다.
- Issue가 지정한 경로와 파일명을 그대로 쓴다. Issue에 없는 산출물은 만들지 않는다.
- 파일 변경은 `siyoungwoo/` 안에서만 한다. 다른 참여자 폴더와 루트 공용 파일은 읽기 전용이다.
- 브랜치는 `weekN/siyoung`, 최신 `origin/main`에서 만들고 `main` 대상으로 PR을 낸다. 본인 PR은 직접 병합하지 않는다.
- 커밋 메시지는 Conventional Commits 접두어 + 한국어 설명이다. 예: `docs: 우시영 week3 보안 취약점 보고서 작성`
- 응답, 문서, PR 본문은 한국어로 쓴다.
- 커밋, 푸시, PR 생성, 리뷰 등록처럼 외부에 보이는 동작은 사용자가 요청했을 때만 한다.

## 3. PR 규칙

- 본문 최상단에 `Issue: #<번호>`를 적는다. `Closes` 같은 closing 키워드는 쓰지 않는다.
- 본문에 Task별 작업 내용, 사용한 AI 에이전트와 모델, 검증 방법과 결과를 적는다.
- 리뷰어는 `juwonlee-dev`, `juhwanHeo` 필수 + 1인 이상을 지정한다.
- 마감 기한 안에 미완성이어도 제출하고, 남은 부분을 본문에 명시한다.

## 4. 작업 원칙

- 먼저 생각한다. 가정은 명시하고, 해석이 갈리면 조용히 고르지 말고 선택지를 제시한다. 불명확하면 멈추고 묻는다.
- 단순하게 한다. 요청받은 것만 만든다. 추측성 기능, 일회용 추상화, 요청 없는 설정 옵션을 넣지 않는다.
- 필요한 곳만 고친다. 주변 문서·코드·서식을 "개선"하지 않는다. 바뀐 모든 줄은 요청으로 설명되어야 한다.
- 목표를 검증 가능하게 정한다. 여러 단계 작업은 `단계 → 확인 방법`으로 계획하고, 확인이 끝나야 완료로 본다.
- 결과는 사실대로 보고한다. 확인하지 못한 것은 확인하지 못했다고 쓴다.

## 5. 보안 분석 규칙 (week3)

- 분석 대상 저장소는 이 저장소 밖 임시 경로에 받는다. 대상 코드는 수정하지 않고, 이 저장소에 복사하지도 않는다.
- 분석 시점의 커밋 해시와 날짜를 보고서에 적는다. 모든 근거는 그 커밋의 `파일:줄`로 표기한다.
- 추측으로 취약점을 만들지 않는다. 코드에서 확인한 사실, 실행으로 재현한 사실, 추정을 구분해 적는다.
- 재현할 수 있는 항목은 PoC로 재현하고 실제 출력만 인용한다. 재현하지 못한 항목은 "미재현"으로 표시한다.
- 의존성 취약점은 기억에 의존하지 않고 공개 DB(OSV 등)를 조회한 결과와 조회일을 적는다. 도달 가능성도 함께 평가한다.
- 위험도는 Critical / High / Medium / Low / Info 5단계로 나누고 판정 기준을 보고서에 명시한다.
- 보고서 첫 장은 단계별 탐지 건수 통계다. 본문 건수와 통계가 일치하는지 마지막에 다시 센다.
- 각 취약점은 `위치 → 설명 → 영향 → 재현 → 조치 방안` 순서로 쓴다. 조치 방안은 현재 소스 기준의 구체적 변경이어야 한다.
- 작성 후 반드시 2차 검토를 한다. 작성 맥락을 모르는 독립 검토자가 근거 줄 번호, 위험도, 오탐, 누락을 다시 확인하고, 그 결과와 반영 내역을 보고서에 남긴다.
- 공격 코드는 재현에 필요한 최소한만 다루고, 보고서에는 원리와 결과 위주로 적는다.
