# juhwan/ 작업 규칙 (study-ai 스터디 과제)

이 폴더는 study-ai(juwonlee-dev/study-ai) 저장소의 juhwan 개인 과제 공간이다.
원칙은 andrej-karpathy-skills의 4원칙(먼저 생각하기, 단순하게, 외과적 변경, 목표 기반 실행)을 따른다.

## 1. 범위와 저장소 규칙
- 수정은 `juhwan/` 아래에서만 한다. 다른 멤버 폴더와 루트 파일은 읽기만 한다.
- 브랜치는 `week{N}/juhwan`. 과제 원문은 `gh issue view {번호} -R juwonlee-dev/study-ai`로 직접 확인한다.
- 과제에 적힌 파일명·경로를 그대로 지킨다(예: `juhwan/week3/REPORT.md`). 임의로 이름을 바꾸지 않는다.
- 커밋은 의미 단위로 나누고 메시지는 `week{N}/juhwan: {한글 설명}`. AI 트레일러(`Co-Authored-By: Claude` 등) 금지.
- PR 본문 최상단은 `Issue: #{번호}`. "Generated with Claude Code" 같은 AI 도구 홍보 문구·링크 금지.
- 로컬 Git 무시 설정에 걸린 새 파일을 과제에서 추적하라고 요구하면 `git check-ignore -v`로 원인을 확인한 뒤 해당 파일만 `git add -f`로 추가한다.
- 커밋·푸시·PR은 사용자가 요청했을 때만 한다.

## 2. 먼저 생각하기 (가정 명시)
- 시작 전에 과제 요구사항을 체크리스트로 옮기고, 해석이 둘 이상이면 고르지 말고 질문한다.
- 가정은 산출물에 "가정:"으로 적는다. 확인하지 못한 사실은 단정하지 않고 "확인 필요"로 표시한다.
- 요구사항끼리 충돌하거나 더 단순한 방법이 있으면 작업 전에 말한다.

## 3. 단순하게
- 요청받은 산출물만 만든다. 요청 없는 부가 파일·도구·스크립트를 추가하지 않는다.
- 보고서는 결론(표·요약)을 먼저, 근거를 뒤에 둔다. 같은 내용을 반복하지 않는다.
- 일반론(“입력 검증을 잘 하자”)은 쓰지 않는다. 모든 주장은 파일:행, 버전, 명령 출력 중 하나로 뒷받침한다.

## 4. 외과적 변경
- 기존 파일은 과제와 관련된 줄만 고친다. 지난 주차 산출물의 서식·내용은 건드리지 않는다.
- 분석 대상 외부 저장소는 읽기 전용이다. 그 저장소의 코드를 고치지 않는다.

## 5. 보안 분석·보고서 작성 규칙 (Task2 류)
- 대상 저장소는 이 저장소 밖 임시 디렉토리(`mktemp -d`)에 clone하고, 분석 시점 커밋 SHA를 보고서에 기록한다.
- 외부 저장소에 이슈·PR·코멘트 등 어떤 것도 게시하지 않는다.
- 실제 공격·원격 대상 스캔은 하지 않는다. 로컬 정적 분석과 로컬 테스트/PoC만 허용한다.
- 오탐 방지: 취약점마다 입력 지점 → 처리 함수 → 위험 지점(sink)까지 실제 호출 경로를 코드로 추적한다.
  경로를 끝까지 확인하지 못했으면 위험도를 낮추거나 "확인 필요"로 남긴다.
- 의존성 취약점은 빌드 파일에 선언된 실제 버전 기준으로 판단한다. CVE 번호는 확인된 것만 적는다.
  전이 의존성 버전은 POM에서 확인하고, OSV 등 조회 출처와 조회일을 적는다.
  CVE가 있어도 대상 코드가 그 기능을 실제로 호출하는지(도달성)를 따로 판단해 위험도에 반영한다.
- PoC·패치 실험 코드는 저장소 밖 scratch 디렉토리에서 작성·실행한다. 보고서에는 실행 출력을 붙인다.
- 위험도는 Critical/High/Medium/Low/Info 5단계, 근거로 CVSS 3.1 벡터와 점수를 함께 적는다.
  라이브러리라면 "호출자가 어떤 입력을 넘길 때" 위험한지 전제를 명시한다.
- 보고서 첫 섹션은 위험도별 탐지 수 통계 표다. 표의 합계는 본문 취약점 수와 반드시 일치시킨다.
- 취약점 항목 형식: ID, 위험도(근거), 위치(파일:행), 설명, 재현/공격 시나리오, 조치 방안(현재 코드 기준 수정 예시).
- 조치 코드는 대상 코드의 실제 클래스·메서드 이름을 써서, 그대로 적용 가능한 형태로 쓴다.
  가능하면 대상의 로컬 사본에 적용해 PoC가 막히고 정상 기능이 유지되는지 확인한다. 못 했으면 "미검증"이라 적는다.
- 오탐으로 판단해 제외한 항목도 근거(파일:행)와 함께 별도 섹션에 남긴다.
- 보고서는 반드시 2차 검토를 거치고, 검토 결과와 반영 내역을 "2차 검토" 섹션에 남긴다.

## 6. 목표 기반 실행 (검증)
- 각 단계에 검증 방법을 붙인다. 예: "통계 표 작성 → 검증: 표 합계 = 본문 `### KP-` 항목 수".
- 파일 작성 후 `wc -l`, `grep -c` 등으로 요구 조건(줄 수, 항목 수)을 실제로 확인한다.
- 행 번호는 `grep -n`/`sed -n`으로 다시 확인한 뒤 적는다. 기억에 의존해 적지 않는다.
- 완료를 보고할 때는 실행한 검증 명령과 결과를 함께 적는다. 실패한 검증은 숨기지 않는다.

## 7. 프롬프트 로그
- `claude-prompt.md`에는 과제 관련 사용자 발화와 AI 응답을 생략 없이 턴 단위로 기록한다.
- 여러 AI/워커를 썼으면 누가 말했는지(사용자/Claude/Codex 워커 등) 구분해서 적는다.
