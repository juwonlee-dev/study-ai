# Codex 작업 지침

이 파일은 `bohye/`와 그 하위 디렉터리에서 수행하는 모든 작업에 적용한다. 특정 주차의 과제 내용보다 사용자 요청과 해당 주차의 GitHub Issue가 우선하며, 서로 충돌하는 지침이 있으면 작업 전에 사용자에게 알리고 확인을 받는다.

## 작업 범위

- 파일 생성, 수정, 삭제, 이동은 `bohye/` 내부에서만 수행한다.
- 다른 참여자의 디렉터리는 관례를 파악하기 위한 읽기 전용 참고 대상으로만 사용하며 수정하지 않는다.
- 저장소 공용 파일이나 `bohye/` 밖의 파일을 변경해야 과제를 수행할 수 있다면 임의로 변경하지 말고 이유와 필요한 변경을 사용자에게 먼저 알린다.
- 명령 실행 시에도 작업 결과물과 임시 파일이 `bohye/` 밖에 생성되지 않도록 한다. 저장소 상태, 브랜치, 이력, Issue 등을 확인하는 읽기 전용 명령은 저장소 루트에서 실행할 수 있다.
- 기존 사용자 변경 사항을 보존하고, 과제와 관련 없는 변경은 수정하거나 되돌리지 않는다.

## 디렉터리와 파일 명명

- 주차별 작업 디렉터리는 `bohye/weekN/` 형식을 사용한다. 예: `bohye/week0/`, `bohye/week1/`.
- GitHub Issue가 파일명이나 경로를 지정하면 그 지정을 우선하여 정확히 따른다.
- Issue에 명명 규칙이 없으면 저장소의 기존 관례와 해당 주차 내 기존 파일 스타일을 따른다.
- `ASSIGNMENT.md`에는 해당 주차의 작업 기준만 기록한다. 모든 주차에 공통으로 적용할 규칙은 이 파일에 둔다.

## 새 주차 시작 절차

1. 저장소 루트와 현재 Git 상태, 현재 브랜치, 기존 변경 사항을 읽기 전용 명령으로 확인한다.
2. `gh issue list`와 `gh issue view`를 사용해 해당 주차의 GitHub Issue를 확인한다. Issue 번호가 불분명하면 제목과 주차를 기준으로 후보를 찾고, 잘못된 Issue를 기준으로 작업하지 않는다.
3. Issue 내용을 다음 항목으로 구분한다.
   - 실제 과제의 목표
   - 필수 요구사항과 완료 조건
   - 경로, 파일명, 도구 사용 등 제약사항
   - 제출해야 할 파일과 기타 제출물
   - 마감 기한과 검증 또는 리뷰 기준
   - 일정, 발표 순서, 패널티 등 구현과 직접 관계없는 운영 안내
4. 과제 내용이 길거나 운영 안내와 섞여 있어 작업 기준이 불명확하면 `bohye/weekN/ASSIGNMENT.md`를 만들고 실제 과제 수행에 필요한 항목만 정리한다. 원문을 임의로 확대 해석하지 않고 Issue 번호와 URL을 함께 기록한다.
5. 기존 저장소 관례에 따라 작업 브랜치 이름으로 `weekN/bohye`를 제안한다. 브랜치 생성은 사용자의 명시적 요청 또는 승인을 받은 뒤에만 수행한다.
6. Issue 또는 `ASSIGNMENT.md`를 기준으로 구현 범위, 작업 순서, 검증 방법을 정리한 뒤 과제를 수행한다.

## 과제 수행 원칙

- 실제 구현과 무관한 운영 안내는 구현 요구사항으로 취급하지 않는다. 다만 마감, 제출 방식, 필수 리뷰어처럼 제출에 영향을 주는 내용은 별도로 보고한다.
- 요구사항이 모호하거나 서로 충돌하면 임의로 결정하지 말고, 확인한 근거와 선택지를 사용자에게 제시한다.
- 과제에서 AI 대화나 프롬프트 기록을 제출하도록 요구하면 지정된 형식과 파일명을 따른다. 기록 파일이 append-only로 지정된 경우 기존 내용을 수정하거나 재정렬하지 않는다.
- 필요한 범위 안에서만 변경하고, 다른 주차의 결과물을 불필요하게 수정하지 않는다.
- 완료 전에는 해당 과제에 적합한 테스트, 실행, 렌더링 또는 정적 검사를 수행한다. 검증할 방법이 없다면 그 사실과 수동 확인 항목을 보고한다.

## Git 및 GitHub 안전 규칙

- `status`, `diff`, `log`, `branch --list`, `show` 등 읽기 전용 Git 명령은 필요한 경우 실행할 수 있다.
- 브랜치 생성 또는 전환, 스테이징, 커밋, 푸시, PR 생성·수정·병합, 태그 생성처럼 저장소나 GitHub 상태를 바꾸는 작업은 사용자의 명시적 요청 또는 승인을 받은 뒤에만 수행한다.
- 사용자가 한 Git 작업을 승인했다고 해서 이후의 다른 Git 작업까지 승인한 것으로 간주하지 않는다. 예를 들어 브랜치 생성 승인은 커밋이나 푸시 승인이 아니다.
- 커밋이 요청되면 `bohye/` 내부의 이번 과제 관련 변경만 포함하고, 다른 참여자나 사용자의 관련 없는 변경은 포함하지 않는다.
- 강제 푸시, 파괴적 reset, 이력 재작성, 브랜치 삭제 등 복구가 어렵거나 협업자에게 영향을 주는 작업은 임의로 수행하지 않는다.
- Git 작업을 실행하지 않은 상태에서는 적절한 브랜치 이름, 커밋 메시지, PR 설명을 제안할 수 있다.

## 완료 및 보고

- 완료 시 변경된 파일, 충족한 요구사항, 수행한 검증과 결과, 남은 문제나 미완료 항목을 사용자에게 간결하게 보고한다.
- Git 상태를 확인해 `bohye/` 밖에 의도하지 않은 변경이 생기지 않았는지 검증한다.
- 커밋, 푸시 또는 PR이 다음 단계로 필요하더라도 자동 실행하지 않고 사용자 지시를 기다린다.
