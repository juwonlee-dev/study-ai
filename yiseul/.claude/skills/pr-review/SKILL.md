# pr-review

study-ai 저장소의 동료 PR을 리뷰하는 절차. 모든 `gh` 명령은 저장소 루트에서 실행한다.

## 0. 인자 처리

- `/pr-review 44` 또는 `/pr-review 44 45`처럼 PR 번호를 주면 그 PR만 대상으로 한다. 1번의 자동 선정은 하지 않는다.
- 번호를 준 PR이 이미 내가 리뷰한 PR이거나 내가 쓴 PR이면, 진행하기 전에 그 사실을 알리고 계속할지 확인한다.
- 번호가 없으면 1번대로 대상을 자동 선정한다.

## 1. 대상 선정

```
gh pr list --state open --json number,title,author,reviewRequests,reviews,updatedAt,baseRefName,headRefName --limit 50
```

- `commits`를 같은 조회에 넣지 않는다. GraphQL 노드 제한 오류가 난다. 커밋은 PR별로 따로 조회한다.
- 내 계정은 `gh api user --jq .login`으로 확인한다.
- 대상: 내가 리뷰하지 않았고, 리뷰가 없거나 내가 리뷰어로 지정된 PR.
- 재요청: `reviewRequests`에 내가 다시 들어 있으면 이전 리뷰 이후 변경을 확인한다. 이전 변경 요청 항목이 해소됐는지 4-1과 같은 방식으로 다시 대조한다.
- 내가 작성한 PR은 제외한다.

## 2. 점검

`gh pr view <N> --json body,files,commits`, `gh pr diff <N>`로 확인한다.

- 이슈 링크: PR 본문에 관련 이슈 번호와 링크(예: `Refs #N`)가 있어야 한다. 이슈가 요구하는 항목이므로 없으면 리뷰 의견에 추가를 요청한다. 앞으로의 이슈에는 이 규칙이 명시되며, 규칙이 명시된 이슈라면 Request changes 사유가 될 수 있다.
- 과제 기준이 되는 이슈 찾기: PR 본문에 링크된 이슈를 쓴다. 링크가 없으면 브랜치 이름의 주차(예: `week2/...`)로 해당 주차 이슈를 `gh issue list`에서 찾아 기준으로 삼는다. 주차 이슈도 찾지 못했을 때는 "기준 이슈를 찾지 못해 조건 대조는 하지 못했다"고 요약 확인에서 알린다.
- 변경 파일이 작성자 본인 폴더 안에 있는지
- `<img>`, `<script>`, 외부 URL 사용 여부 (이슈 조건에 따라)
- prompt.md가 프롬프트와 AI 응답을 생략 없이 담았는지 (요약이나 표로 대체됐는지)
- PR 본문: 사용 AI와 도구, 리뷰어 지정, 검증 내용
- 커밋 메시지: 필요한 경우에만
- 다른 리뷰어가 이미 지적한 내용은 확인하고, 중복이면 동의한다고 짧게 적는다.
- 직접 확인하지 못한 항목(이미지 렌더링 등)은 단정하지 말고 못 봤다고 밝힌다.

## 3. 스택형 PR(Stacked PR) 처리

`baseRefName`이 `main`이 아니면 다른 PR 브랜치 위에 쌓인 PR이다.

- base 브랜치를 head로 가진 PR(부모)을 찾아 `main <- A <- B <- C` 순서로 정리해 사용자에게 보여준다.
- 리뷰는 부모부터 한다. `gh pr diff`가 자기 변경분만 보여 주는지 확인하고, 부모 변경분이 섞여 보이면 그 PR의 잘못으로 단정하지 않는다.
- 부모가 수정되면(force-push, 리베이스) 자식 PR이 최신이 아닐 수 있으므로 재승인 판단 시 부모의 변경 여부도 확인한다.
- 부모가 먼저 병합되어야 한다는 점을 리뷰와 보고에 적는다. 병합은 임의로 하지 않는다.
- 스택이 길어 리뷰가 어렵다면 PR 본문에 스택 순서와 부모 PR 링크를 적도록 제안한다.

## 4. 판정

- 내가 리뷰어이고 큰 문제가 없으면 Approve
- 이슈에 명시된 조건 위반 등 수정이 필요하면 Request changes
- 그 외(리뷰어가 아닌데 의견만 남기는 경우)는 Comment

### 4-1. Request changes일 때 소스 비교와 보완 요청

수정이 필요하다고 판단한 항목만, 근거가 되는 소스와 직접 대조해 구체적으로 요청한다. Approve는 짧게 쓰고 전체 코드 리뷰는 하지 않는다.

- 대조 대상: 이슈 본문 조건(`gh issue view <번호>`), 원본 자료(예: `week1/profile.png`, README), PR diff, 제출 기록(prompt.md)
- 요청 형식: 어디(파일, 위치)가, 무엇과 달라서(이슈 조건 또는 원본), 어떻게 고치면 되는지를 항목별로 1~3개 적는다. 고치는 방법도 함께 쓴다. 예: "프롬프트 4의 응답 전문을 턴 순서대로 추가해 주세요."
- 확인하지 않은 추정은 요청하지 않는다.

## 5. 초안 형식

- 이모티콘은 쓰지 않는다.
- 잘한 점 한 단락 + 의견 2~3개로 간략하게 쓴다.
- 의견에 담을 것: 프롬프트 작성 방식(스킬 사용, 지침 작성, 토큰 절약이나 작업 단축 방법), PR 본문의 부족한 점과 잘된 점, 과제를 이렇게 만들었으면 더 좋았을 것이라는 의견
- 이슈 조건을 지켰고 문제가 없는 항목은 쓰지 않는다. 커밋 메시지는 필요할 때만 언급한다.
- "Claude Code로 리뷰했습니다" 같은 AI 서명 문구는 넣지 않는다.

## 6. 등록 전 요약 확인 (필수)

등록하기 전에 먼저 아래를 요약해서 보여주고 사용자의 확인을 받는다.

- 대상: 누구의 어떤 PR(#번호, 제목)을 왜 골랐는지(리뷰어 지정, 리뷰 없음, 재요청), 제외한 PR과 이유
- 방식: PR별 판정과 핵심 근거, 점검한 항목, 직접 확인하지 못한 항목

그다음 초안 전문을 보여주고, 승인을 받은 뒤에만 등록한다. 재승인처럼 짧은 리뷰는 한 줄 본문으로 쓴다.

## 7. 등록과 검증

```
gh pr review <N> --approve --body-file -
gh pr review <N> --request-changes --body-file -
```

본문은 heredoc으로 넘긴다. 등록 후 내 최신 상태를 확인하고 PR별로 보고한다.

```
gh api repos/<owner>/<repo>/pulls/<N>/reviews --jq '[.[]|select(.user.login=="<내 계정>")]|map(.state)'
```
