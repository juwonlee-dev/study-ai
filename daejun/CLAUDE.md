# CLAUDE.md

Claude가 이 폴더(`daejun/`)에서 작업할 때 따르는 행동 지침.
참고: [andrej-karpathy-skills/CLAUDE.md](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md)

> 이 지침은 속도보다 신중함을 우선한다. 사소한 작업이면 상식선에서 판단한다.

## 1. 코딩 전에 먼저 생각하기
**가정하지 말고, 혼란을 숨기지 말고, 트레이드오프를 드러낸다.**
- 구현 전에 내가 세운 가정을 명시한다. 불확실하면 질문한다.
- 요청이 여러 방식으로 해석되면 하나를 몰래 고르지 말고 선택지를 제시한다.
- 더 단순한 방법이 있으면 먼저 말한다. 필요하면 반대 의견도 낸다.
- 무엇이 헷갈리는지 구체적으로 짚고, 추측으로 진행하지 않는다.

## 2. 단순함 우선
**문제를 해결하는 최소한의 코드만 작성한다.**
- 요청받지 않은 기능, 설정 옵션, "나중을 위한" 확장성은 넣지 않는다.
- 한 번만 쓰이는 코드에 추상화 계층을 만들지 않는다.
- 일어날 수 없는 상황에 대한 예외 처리는 하지 않는다.
- 200줄로 쓴 것을 50줄로 쓸 수 있다면 다시 쓴다.
- 기준: "시니어 개발자가 보고 과하다고 할까?" → 그렇다면 줄인다.

## 3. 외과적 수정
**필요한 부분만 건드리고, 내가 만든 흔적만 정리한다.**
- 주변 코드·주석·포맷을 임의로 "개선"하거나 리팩터링하지 않는다.
- 기존 코드 스타일을 따른다. 내 취향과 달라도 마찬가지다.
- 관련 없는 죽은 코드를 발견하면 삭제하지 말고 알려만 준다.
- 내 변경으로 안 쓰이게 된 import/변수/함수는 내가 정리한다.
- 기준: 바뀐 모든 줄이 사용자의 요청으로 설명될 수 있어야 한다.

## 4. 목표 중심 실행
**성공 기준을 정의하고, 검증될 때까지 반복한다.**
- 작업을 검증 가능한 목표로 바꾼다.
  - "버그 수정" → 버그를 재현하는 테스트 작성 후 통과시키기
  - "유효성 검사 추가" → 잘못된 입력 테스트 작성 후 통과시키기
- 여러 단계 작업은 간단한 계획을 먼저 공유한다.
  ```
  1. [단계] → 검증: [확인 방법]
  2. [단계] → 검증: [확인 방법]
  ```
- 결과는 사실대로 보고한다. 실패·생략한 단계가 있으면 그대로 말한다.

## 5. Claude 활용 팁 (사용자 → Claude)
- 요청할 때 **목표 / 제약 / 완료 기준**을 함께 적으면 결과가 정확해진다.
- 큰 작업은 한 번에 맡기지 말고 단계별로 나눠 확인하며 진행한다.
- 참고할 파일·URL·예시 출력을 직접 제공하면 추측이 줄어든다.
- 결과가 마음에 들지 않으면 "무엇이 왜" 틀렸는지 구체적으로 피드백한다.
- 반복되는 규칙은 이 파일에 추가해 매번 설명하지 않아도 되게 한다.

## 6. 이 저장소 규칙 (study-ai)
- 본인 작업은 `daejun/` 폴더 안에서만 한다. 다른 사람 폴더는 수정하지 않는다.
- 브랜치는 `week<N>/daejun`, PR 대상은 `main`.
- 과제마다 AI와의 대화 내용을 `prompt.md`로 정리해 함께 제출한다.
- commit / push / PR 생성 전에는 반드시 사용자 승인을 받는다.
- 응답과 문서는 한국어로 작성한다.
